Google Analytics

Metrics derived from the CanadaLogin GA4 property, in the google_analytics schema. See the Data Catalog for the underlying tables.

Task success rates are computed from GA4 funnels: named, ordered sequences of page or event steps, defined as version-controlled YAML rather than a private GA4 UI exploration. A funnel’s exact steps can change as CanadaLogin’s own pages change, so metrics on this page describe the general calculation and point to that YAML on GitHub as the definitive, current source, rather than hard-coding step names that may already be out of date by the time they’re read.

Task Success Rate

The proportion of users who started a given task in CanadaLogin and reached that task’s defined finishing point, measured from Google Analytics 4 funnel data.

This is a family of metrics, not a single number: each funnel declares its own task success rate as a step_ratio in its YAML definition on GitHub - one funnel step counted as the entry, another counted as the exit, both measured as GA4 activeUsers over the same reporting window. The entry and exit steps for each funnel are described below as of this writing, but the YAML is the canonical, versioned source - see funnel_src/funnels/ in the canadalogin-reporting-data-pipeline repo. Check the YAML before trusting a step name quoted here.

Alternative names:

  • funnel completion rate
  • task completion rate
  • funnel success rate

Sign in

Funnel definition: sign_in.yaml.

Entry is the first taggable step of the sign-in flow (the “enter your email” screen); exit is reaching MFA selection, the last step Google Analytics can see. This is not a full sign-in completion rate. A successful sign-in redirects off-site to IBM Verify and back to the relying party with no page in between, so GA4 has no event to mark true completion - reaching MFA is the closest proxy available. See the funnels catalog entry for the RESERVED_TOTAL and window_incomplete conventions this table shares with funnel_metrics.

Sign up

Funnel definition: sign_up.yaml.

Entry is the first step of the sign-up flow, after accepting Terms and Conditions; exit is the account-creation confirmation screen. Unlike sign-in, this is a true completion signal - the confirmation page is a real, first-party GA4 event.

Calculation. Each funnel’s task success rate is already computed and stored as one row per window in funnel_metrics: the exit step’s activeUsers divided by the entry step’s, for that funnel run. There is no ratio to compute by hand - filter to the funnel and metric, and read value. Query funnel_metrics_current rather than funnel_metrics directly, so a future funnel version bump can’t silently blend two definitions together. Filter breakdown_value = 'RESERVED_TOTAL' for the overall rate across all relying parties; substitute a specific relying party name for a per-RP figure.

Sign in:

SELECT
    window_end,
    value AS task_success_rate
FROM google_analytics.funnel_metrics_current
WHERE funnel_id = 'sign_in'
  AND metric_id = 'task_success'
  AND window_days = '7'
  AND breakdown_value = 'RESERVED_TOTAL'
  AND NOT window_incomplete
  -- set the reporting window; see the timespans note in cookbook/notes.qmd
  AND CAST(window_end AS DATE) BETWEEN DATE '2026-07-14' AND DATE '2026-08-03'
ORDER BY window_end;

Sign in:

tbl(con, in_schema("google_analytics", "funnel_metrics_current")) |>
  filter(
    funnel_id == "sign_in",
    metric_id == "task_success",
    window_days == "7",
    breakdown_value == "RESERVED_TOTAL",
    !window_incomplete,
    # set the reporting window; see the timespans note in cookbook/notes.qmd
    as.Date(window_end) >= as.Date("2026-07-14"),
    as.Date(window_end) <= as.Date("2026-08-03")
  ) |>
  select(window_end, task_success_rate = value) |>
  arrange(window_end)

Sign up:

tbl(con, in_schema("google_analytics", "funnel_metrics_current")) |>
  filter(
    funnel_id == "sign_up",
    metric_id == "task_success",
    window_days == "7",
    breakdown_value == "RESERVED_TOTAL",
    !window_incomplete,
    # set the reporting window; see the timespans note in cookbook/notes.qmd
    as.Date(window_end) >= as.Date("2026-07-14"),
    as.Date(window_end) <= as.Date("2026-08-03")
  ) |>
  select(window_end, task_success_rate = value) |>
  arrange(window_end)

Interpretation notes. The queries above use window_days = '7', a rolling weekly rate recomputed nightly on a 7-day window ending each date. Three window lengths exist, and switching between them is a one-line change:

  • '1' is the same metric on a single day. It is the noisiest of the three, but it is the only one that shows the exact date something changed.
  • '7' is the usual default. Every window holds one of each weekday, so day-of-week effects wash out.
  • '28' is a rolling four-week window. It is the steadiest of the three and the one to use for monthly reporting, but a step change takes 28 days to show up in it fully, so it is a poor way to check whether a fix worked.

All three are partition-key strings, not numbers, in this schema. Windows within one window_days overlap, so consecutive rows are not independent readings: one unusual day moves 7 weekly rows and 28 monthly ones. A value of NULL means nobody reached the entry step that window (an undefined rate, not a true zero) - such rows are rare but real, and an average that treats them as 0.0 will read too pessimistic.

These two funnels are not directly comparable to each other: sign-in’s rate stops at MFA for the structural reason described above, so it reads lower than a true completion rate would, while sign-up’s rate is a real completion figure. Comparing the two numbers as if they measured the same kind of finish line will overstate the sign-in/sign-up gap.
