Google Analytics

Tables in the google_analytics schema, populated from the CanadaLogin GA4 property. Three scheduled Lambdas write into this schema each night, all in the canadalogin-reporting-data-pipeline repo’s google_analytics Terraform module:

  • 06:30 ET - the funnel export, writing funnels
  • 06:45 ET - the funnel metrics Lambda, deriving funnel_metrics from the funnels the export just landed
  • 07:00 ET - the daily export, writing property_traffic and page_traffic, then starting the crawler

funnels_current and funnel_metrics_current are views over funnels and funnel_metrics respectively, resolving each date to its current funnel version.

Export lag

funnels and funnel_metrics are pulled with a deliberate two-day lag - the nightly sweep that runs the morning of August 5, 2026 lands a window ending August 3, 2026, not August 4 - because GA4 takes 24 to 48 hours to finish processing a day’s events (backdated hits accepted up to 72 hours), and since each (funnel_version, window_end) key is written once and never re-pulled, a window read too early would stay artificially low forever. property_traffic and page_traffic carry no equivalent lag - their export asks GA4 for “yesterday” every morning with no wait and no later re-pull - so their most recent day can undercount for the same reason, with nothing to ever correct it.

Two of these tables - funnels and funnel_metrics - are defined by version-controlled YAML rather than a fixed schema. For what a funnel step or a derived metric actually measures, the YAML on GitHub is the single canonical source, not this catalog: steps get renamed, re-scoped, or added as CanadaLogin’s own pages change, and the catalog entries below describe the table shape rather than the current step names. See funnel_src/funnels/ in the pipeline repo.

property_traffic

Property-wide daily traffic for the CanadaLogin GA4 property, with no dimension beyond the day.

Each row represents one day of aggregate site-wide traffic.

Keywords: Google Analytics, GA4, traffic, sessions, active users, page views

Provenance

Pulled daily from the GA4 Data API (runReport) for the CanadaLogin property, via a Lambda authenticating through Google Cloud Workload Identity Federation (no stored service account key). Written as JSONL, then cast to typed Parquet by a Glue ETL job.

  • Updated: Daily, at 07:00 ET
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas
  • Location: s3://<transformed-bucket>/google_analytics/property_traffic/

Fields

One row per date.

Field Name Type Description
date string The reporting day, as a partition key (for example, “2026-07-23”)
sessions bigint Number of sessions started on this day, site-wide
activeusers bigint Number of distinct active users on this day, site-wide
newusers bigint Number of users on this day who had not been seen before
screenpageviews bigint Number of page views on this day, site-wide

Notes

activeusers is de-duplicated by GA4 within the day; it is not the sum of per-page unique users. This table is the collection canary for the GA4 pipeline: because it carries no dimension beyond date, a property-wide active-user collapse here distinguishes “GA stopped collecting” from “one page or one funnel’s tag broke,” which page_traffic rows alone cannot do.

screenpageviews here should equal SUM(screenpageviews) from page_traffic for the same date - the two tables’ only currently-summable metric, and a useful integrity check between them. sessions and activeusers do not reconcile the same way across the two tables (GA4 de-duplicates each within its own dimension combination), so do not expect them to match.

page_traffic

Daily traffic for the CanadaLogin GA4 property, broken down by page.

Each row represents one day of traffic to a single page, identified by both its title and its path.

Keywords: Google Analytics, GA4, page views, traffic, page title, page path

Provenance

Pulled daily from the GA4 Data API (runReport) for the CanadaLogin property, via the same Lambda and pipeline as property_traffic.

  • Updated: Daily, at 07:00 ET
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas
  • Location: s3://<transformed-bucket>/google_analytics/page_traffic/

Fields

One row per date per pagetitle per pagepath.

Field Name Type Description
date string The reporting day, as a partition key (for example, “2026-07-23”)
pagetitle string The page’s <title> at the time of the visit
pagepath string The page’s URL path
sessions bigint Number of sessions that included this page on this day
activeusers bigint Number of distinct active users who viewed this page on this day
screenpageviews bigint Number of times this page was viewed on this day

Notes

Keep both pagetitle and pagepath in mind when joining or filtering. Title alone is an unstable key: a page retitled in a release starts a fresh row with no link to its history (this has happened repeatedly to CanadaLogin’s sign-in and sign-up pages - see the task success rate metric for the concrete impact). Path alone is unreadable in a report. Prefer pagepath for anything that needs to survive a copy or title change.

activeusers does not sum across pages. GA4 de-duplicates active users within a row’s dimension combination, so a user who visited three pages in a day appears in all three rows. Summing activeusers across pages, or across this table and property_traffic, overcounts. sessions and screenpageviews are safe to sum; see the property_traffic integrity-check note.

screenpageviews exposes per-step retries on a form page (views greater than 1 on a single page in a day is a friction signal invisible in a funnel’s pass/fail step counts).

funnels

Step-by-step counts for each defined GA4 funnel (currently sign_in and sign_up), for a given reporting window.

Each row represents one step of one funnel run, for one relying party (or the funnel’s total across all relying parties).

Keywords: Google Analytics, GA4, funnel, funnel step, task success, drop-off, abandonment, relying party

Provenance

A funnel is defined as YAML, not SQL: one file per funnel in funnel_src/funnels/ in the canadalogin-reporting-data-pipeline repo. A dedicated Lambda turns each funnel’s YAML into a GA4 Data API runFunnelReport request (via Workload Identity Federation, same auth pattern as property_traffic) and writes the result as JSONL. The YAML on GitHub is the canonical definition of what each funnel measures - which pages or events count as which step, in what order, and over what population. This page describes the table shape; it does not enumerate step names, because they are versioned in that YAML and can change between funnel versions.

  • Updated: Daily, at 06:30 ET (a nightly sweep; see Notes)
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas
  • Location: s3://<transformed-bucket>/google_analytics/funnels/

Fields

One row per funnel_id per funnel_version per window_days per window_end per funnelstepname per breakdown_value.

Field Name Type Description
funnel_id string Partition key. Which funnel this row belongs to (for example, “sign_in”, “sign_up”) - matches a filename under funnel_src/funnels/ on GitHub
funnel_version string Partition key. The funnel definition’s version at the time this row was run. A plain integer, but typed string by the crawler - see Notes
window_days string Partition key. Length of the reporting window this row summarizes: “1” for a nightly monitoring run, “7” for a rolling weekly rate
window_end string Partition key. Last date (inclusive) of the reporting window, as text (for example, “2026-07-23”)
funnelstepnumber bigint The step’s 1-indexed position in the funnel
funnelstepname string The step’s name, as declared in the funnel’s YAML on GitHub. Not a closed set - see Provenance
breakdown_dimension string The bare GA4 dimension a funnel’s breakdown: block splits by (currently always “rp_name”, the relying party)
breakdown_value string The relying party this row covers, or the sentinel RESERVED_TOTAL for the funnel’s grand total across all relying parties (including any past GA4’s 15-value breakdown cap) - see Notes
activeusers bigint Distinct active users who reached this step, for this relying party, within the window
funnelstepcompletionrate double GA4’s own step-over-step completion rate (this step’s users over the previous step’s)
funnelstepabandonments bigint Users who reached this step but did not reach the next one
funnelstepabandonmentrate double funnelstepabandonments as a proportion of this step’s activeusers
window_start string First date (inclusive) of the reporting window, as text. Derivable from window_end and window_days, but stored for convenience
window_incomplete boolean true if this window was trimmed to the funnel’s valid_from/valid_to bounds (see Notes) - exclude these rows from any trend read as a full window

Notes

A funnel’s step names, order and population can change between versions - always check GitHub, not a memory of a prior version. Every CanadaLogin funnel has already had at least one step renamed or re-scoped since it was first defined (see the task success rate metric for a worked example). funnel_version exists so old and new definitions coexist rather than silently overwriting each other: always pin funnel_version in a query, or use the funnels_current view, which resolves the newest version per date automatically. Summing or averaging across versions blends two different definitions of the funnel into one meaningless number.

RESERVED_TOTAL is a real GA4 sentinel, not a relying party. A funnel breakdown caps at 15 distinct values; RESERVED_TOTAL is GA4’s grand total across all relying parties, including any beyond that cap, and is the correct number to read as the funnel’s overall rate.

window_incomplete rows are written, not dropped, and must be excluded from a trend. A window that reaches earlier than a funnel’s valid_from (or later than valid_to) is trimmed and flagged rather than skipped, so a scheduled job keeps running as a tagging boundary recedes. A trimmed 7-day row is still labelled window_days = "7" but covers fewer than 7 days - reading it as a full week understates or overstates the true rate depending on what changed at the boundary.

activeusers is de-duplicated within its own window and is not additive across windows. Summing seven daily (window_days = "1") rows for a week is not the same query as one window_days = "7" row for that week - repeat users within the week are counted once by the 7-day row and once per day they appeared by the daily rows. Rates hold close either way; raw counts do not. Never sum activeusers across rows with different window_end values.

The nightly 06:30 ET run also self-heals: on a funnel_version bump, it backfills every past window still needed under the new version, so the “Updated” cadence above describes when new dates land, not necessarily when every partition was last (re)written.

funnels_current

A view over funnels that resolves the current funnel_version automatically. Query this instead of funnels directly unless a specific past version is genuinely what’s wanted.

Each row is the same as a funnels row, restricted to the newest funnel_version available for that row’s (funnel_id, window_days, window_end).

Keywords: Google Analytics, GA4, funnel, funnel version, current version

Definition

CREATE OR REPLACE VIEW funnels_current AS
WITH latest_per_date AS (
  SELECT funnel_id, window_days, window_end,
         MAX(CAST(funnel_version AS integer)) AS current_version
  FROM funnels
  GROUP BY funnel_id, window_days, window_end
)
SELECT f.*
FROM funnels f
JOIN latest_per_date d
  ON  f.funnel_id   = d.funnel_id
  AND f.window_days = d.window_days
  AND f.window_end  = d.window_end
  AND CAST(f.funnel_version AS integer) = d.current_version;

Provenance

  • Updated: Live view, not scheduled
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas

Fields

Same as funnels. SELECT f.* passes every base column through unchanged; the view’s own current_version column (used only to resolve the join) is not exposed.

Notes

The partition keys are still typed string in the view’s output, the same as the base table - MAX(funnel_version) on the view still sorts lexically wrong if you ignore that the view has already picked one version per row. Query it the same way you’d query funnels: filter with quoted string literals (WHERE window_days = '7', not = 7), and don’t re-aggregate across funnel_version since the view has already resolved it.

Resolution is per (funnel_id, window_days, window_end), not a global max per funnel. If a funnel bumps from version 1 to version 2 partway through its history, dates before the bump still resolve to version 1 (version 2 was never run for them) and dates from the bump onward resolve to version 2 - one continuous time series, not a series that vanishes before the bump. This only holds because versions of the same funnel are assumed to measure the same underlying thing; it would not be a safe pattern for two versions that represent genuinely different metrics.

funnel_metrics

Derived metrics computed from landed funnels rows - currently task success rates, one per funnel.

Each row represents one metric’s value, for one funnel run, for one relying party (or the funnel’s total across all relying parties).

Keywords: Google Analytics, GA4, funnel, task success, task success rate, derived metric

Provenance

Like a funnel’s steps, a funnel’s derived metrics are declared in that funnel’s YAML on GitHub, in a metrics: block - see funnel_src/funnels/ in the canadalogin-reporting-data-pipeline repo. The YAML is the canonical definition of what each metric measures, including which two steps a ratio divides. A separate Lambda reads the already-landed rows from funnels (no new GA4 call) and computes every metric each funnel declares. See the task success rate cookbook entry for how the one metric type in use today (step_ratio) is calculated and interpreted.

  • Updated: Daily, at 06:45 ET, after the 06:30 ET funnel export
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas
  • Location: s3://<transformed-bucket>/google_analytics/funnel_metrics/

Fields

One row per funnel_id per funnel_version per window_days per window_end per metric_id per breakdown_value.

Field Name Type Description
funnel_id string Partition key. Which funnel this metric was computed from (for example, “sign_in”, “sign_up”)
funnel_version string Partition key. The funnel definition’s version the metric was computed under. Typed string by the crawler - see the funnels Notes
window_days string Partition key. Length of the reporting window: “1” (nightly monitor) or “7” (rolling weekly rate)
window_end string Partition key. Last date (inclusive) of the reporting window, as text
metric_id string Which metric this row is. Declared per-funnel on GitHub; currently always “task_success” for both funnels, but not a closed set - see Provenance
metric_type string The metric’s calculation shape, from the same YAML declaration. Currently always “step_ratio” (one step’s activeusers over another’s)
value double The computed metric value. null, not 0.0, when the denominator is zero (nobody entered, so the rate is undefined - not a false zero)
breakdown_dimension string The bare dimension the source funnel’s breakdown: block splits by (currently always “rp_name”)
breakdown_value string The relying party this row covers, or RESERVED_TOTAL for the funnel’s overall value - see funnels Notes
window_start string First date (inclusive) of the reporting window, as text
window_incomplete boolean true if the underlying funnel window was trimmed to valid_from/valid_to - exclude these rows from a trend, same rule as funnels

Notes

This table deliberately does not carry the raw step values a ratio was computed from - only the result. The inputs are recoverable by joining back to funnels on the same (funnel_id, funnel_version, window_days, window_end, breakdown_value), if they’re needed.

Same versioning caveat as funnels, and the same fix applies: always pin funnel_version, or query funnel_metrics_current rather than this table directly.

A metric is recomputed automatically when its funnel’s funnel_version bumps (the same nightly job backfills every past window under the new version), but adding a metrics: block to a funnel for the first time also triggers a one-time backfill across that funnel’s entire already-landed history - so a metric’s earliest window_end is not necessarily the date the metric was defined.

funnel_metrics_current

A view over funnel_metrics that resolves the current funnel_version automatically, the same way funnels_current does for funnels. Query this instead of funnel_metrics directly unless a specific past version is genuinely what’s wanted.

Each row is the same as a funnel_metrics row, restricted to the newest funnel_version available for that row’s (funnel_id, window_days, window_end).

Keywords: Google Analytics, GA4, funnel, task success, funnel version, current version

Definition

CREATE OR REPLACE VIEW funnel_metrics_current AS
WITH latest_per_date AS (
  SELECT funnel_id, window_days, window_end,
         MAX(CAST(funnel_version AS integer)) AS current_version
  FROM funnel_metrics
  GROUP BY funnel_id, window_days, window_end
)
SELECT f.*
FROM funnel_metrics f
JOIN latest_per_date d
  ON  f.funnel_id   = d.funnel_id
  AND f.window_days = d.window_days
  AND f.window_end  = d.window_end
  AND CAST(f.funnel_version AS integer) = d.current_version;

Provenance

  • Updated: Live view, not scheduled
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas

Fields

Same as funnel_metrics. SELECT f.* passes every base column through unchanged; the view’s own current_version column (used only to resolve the join) is not exposed.

Notes

Same query rules as funnels_current: partition key literals still need quotes (window_days = '7', not = 7), and don’t re-aggregate across funnel_version since the view has already resolved it.
