Relying Parties

Reference tables for identifying and grouping the services that use CanadaLogin, in the rp schema. They hold no measurements. They exist to give the analytics tables a shared service identifier, so that IBM Verify sign-in counts and Google Analytics funnel steps can be reported against the same list of services.

service holds one row per relying party, with its names, operator, and launch date. alias maps each of the many strings the source systems use for a service back to that service’s rp_id.

Both tables come from one hand-maintained Google Sheet, read every weekday by the rp-sync Lambda in cds-snc/canadalogin-reporting-data-pipeline. That pipeline owns the table structure. Do not change it from this side.

Joining through the lookup

Resolve a source-system name to a relying party by joining on alias, then join rp_id to service for the attributes:

SELECT s.service_name_en,
       sum(a.successful_logins) AS successful_logins
FROM ibm_verify.app_login_counts a
JOIN rp.alias al ON a.application_name = al.alias
JOIN rp.service s ON al.rp_id = s.rp_id
WHERE a.from_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31'
GROUP BY s.service_name_en

Aggregate after the join, never before. Several IBM Verify application names can map to one service, so a pre-aggregated count keyed on application_name will split a service across its environments.

Data quality

Because the source is a hand-maintained spreadsheet, a few caveats apply to both tables:

  • The list is not a complete inventory. Services are added when they appear in IBM Verify or analytics data, so a live service with no traffic yet will be missing.
  • New names need a manual edit. An application name that appears in IBM Verify before someone adds it to the sheet will not resolve, and an inner join will drop its rows without complaint. Left join and check for nulls when you care about coverage.
  • Free-text columns are unvalidated. service_name_en, service_name_fr, and operator are typed by hand, so expect occasional drift in spelling and spacing. Group by gc_orgid rather than operator.
  • Neither table keeps history. Each refresh overwrites the previous one, so a service renamed in the sheet is renamed retroactively for every report.

service

One row per relying party: a service that uses CanadaLogin to sign its users in. Services that run more than one application in CanadaLogin appear once here, not once per application.

Keywords: Relying party, RP, service, application, department, operator, GC org

Provenance

The list is maintained by hand in the CanadaLogin Relying Parties Google Sheet. The rp-sync Lambda reads the sheet every weekday and writes a single Parquet file to S3, then triggers a Glue crawler to refresh the table in Athena. The table is not partitioned and the file is overwritten in place, so this table holds current state only and keeps no history.

  • Updated: Weekdays, at 06:00 ET
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas
  • Location: s3://canadalogin-reporting-transformed/rp/service/

Fields

Field Name Type Description
rp_id bigint Identifier for the relying party. Assigned by hand in the source sheet and stable across refreshes. Joins to rp.alias.rp_id.
service_name_en varchar English name of the service. Free text.
service_name_fr varchar French name of the service. Free text.
operator varchar The organization that runs the service, typed by hand. Display only, see the note below.
gc_orgid bigint The gc_orgID of the operating organization, or 0 for entities that are not in the originating dataset.
is_internal boolean Is the service internal facing, rather than something the public signs in to?
launch_date varchar Approximate date the service launched to the public, as YYYY-MM-DD. Stored as text.
fetched_at timestamp(3) When the Lambda last read the source sheet, in UTC.

Notes

Group by gc_orgid, not operator. gc_orgid comes from the GC Organization Names and Codes dataset. IDs can be resolved to bilingual names through that dataset or the companion tool, cds-snc/gcorg-resolver.

gc_orgid = 0 means not applicable. The organization running the service has no entry in the GC organization dataset, so there is no ID to record. For these rows, group on the operator value instead.

launch_date is a string, so cast both sides when comparing. Comparing it against an R value that looks like an ISO date fails with TYPE_MISMATCH: Cannot apply operator: varchar = date, because RAthena casts ISO-format strings to a SQL DATE literal.

This is not a complete inventory of relying parties. A service is added to the sheet when it shows up in IBM Verify or the analytics data, so a service that is live but has no traffic yet will be missing. Do not use count(*) here as the denominator for “how many services use CanadaLogin”.

alias

One row per name that refers to a relying party. The same service is called different things in different systems, and this table maps each of those strings back to a single rp_id.

Use it to join tables that have no shared service identifier, such as ibm_verify.app_login_counts.application_name and the rp_name breakdown in the Google Analytics funnel tables.

Keywords: Relying party, RP, alias, application name, crosswalk, lookup, join

Provenance

Maintained by hand in the same CanadaLogin Relying Parties Google Sheet as rp.service, read every weekday by the same Lambda and written as a single Parquet file. Not partitioned, overwritten in place, current state only.

  • Updated: Weekdays, at 06:00 ET
  • Steward: EDCP Data and Research Team
  • Contact: Colin Douglas
  • Location: s3://canadalogin-reporting-transformed/rp/alias/

Fields

Field Name Type Description
alias varchar The string that refers to the service, exactly as the source system writes it.
rp_id bigint The relying party this alias refers to. Joins to rp.service.rp_id.
source varchar Where the alias was first encountered, one of IBM Verify or Google Analytics. Record keeping only, see the note below.
fetched_at timestamp(3) When the Lambda last read the source sheet, in UTC.

Notes

Join on alias alone. Do not filter on source. source records where the name was first seen, not which system the name belongs to. Filtering by it before joining will silently drop matches for any alias that turns up in both systems.

One service, several aliases. A service has as many rows here as it has names. For example, MyCGC is MyCGC in Google Analytics but both MyCGC - CGC - .NET - Prod and MyCGC - CGC - Power Pages - Prod in IBM Verify. Joining a fact table through this lookup is a many-to-one join, so aggregate after the join, not before.

Not every string in the analytics tables is an alias. The rp_name breakdown in the Google Analytics funnel tables also contains RESERVED_TOTAL (the all-services rollup), (not set), and the empty string. None of these are services, and an inner join drops them. If you are reconciling totals, exclude RESERVED_TOTAL explicitly rather than relying on the join to remove it.

Aliases are exact strings, not patterns. They are matched literally, with no trimming or case folding. A new application name in IBM Verify will not resolve until it is added to the source sheet by hand.
